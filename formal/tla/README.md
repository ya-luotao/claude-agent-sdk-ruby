# TLA+ models

Two small [TLA+](https://lamport.azurewebsites.net/tla/tla.html) models of the SDK's most concurrency-sensitive designs, checked with TLC. They are design documentation that a machine checks, not a proof about the Ruby code: each one models the algorithm a source comment argues for, shows it holds over every interleaving within the model's bounds, and shows that the alternatives the comments warn against really do break.

```bash
formal/tla/run.sh                                   # every config, compared with its expected outcome
formal/tla/run.sh cli_installer/bug_order.cfg       # one config, with TLC's full counterexample trace
JAVA=/opt/homebrew/opt/openjdk/bin/java formal/tla/run.sh   # if the java on PATH is older than 11
```

`run.sh` downloads the pinned `tla2tools.jar` (v1.8.0, SHA-256 checked) into `formal/tla/.tools/` on first use and needs Java 11+. The whole run takes under a minute. Nothing here is shipped in the gem.

Each model has boolean switches. With all of them `TRUE` you get the shipped design, which must pass. Setting one to `FALSE` gives the alternative that a source comment rejects, and TLC must find a counterexample for it. The `reach_*` configs assert that something never happens (an upgrade, a crash leftover, an error outcome) and are expected to fail. They show that the model actually reaches the states the properties talk about, so a `pass` is not vacuous.

## `CLIInstaller.tla`: install, publish, sweep

Models `CLIInstaller.install` / `#publish` (`lib/claude_agent_sdk/cli_installer.rb`): several processes install into one `vendor/claude` at once. Every fallible step can raise, running its `ensure`, and any process can be killed at any point, which skips `ensure` but releases its flock. The `stable` dist-tag moves forward while they run.

| Config | Switch | Result | The comment it checks |
|---|---|---|---|
| `good`, `good_big` | all `TRUE` | pass (2 installers × 2 runs; 3 × 3) | |
| `bug_order` | `RECORD_BEFORE_RENAME = FALSE` | `NeverLoseWorkingInstall` violated: v1 installed; the v2 upgrade renames, then its metadata write fails and the cleanup deletes the binary, leaving the directory with none | `#publish`: "The reverse order — rename then record — … taking the previous working install with it" |
| `bug_resolve` | `RESOLVE_IN_LOCK = FALSE` | `NoDowngrade` violated: A reads tag 1, B installs 2, A takes the lock and installs 1 | `install`: "RESOLVED inside the lock … Semantics: last resolver wins" |
| `bug_sweep` | `SWEEP_IN_LOCK = FALSE` | `LiveDownloadsIntact` violated: one installer's sweep deletes another's in-flight download | `sweep_stale_temp_files`: "Safe because we hold the install lock" |

Properties: `ReadersSeeVerifiedBinary` (a lock-free reader never sees a partial or unverified binary), `NeverLoseWorkingInstall` (once an install has completed, a failed later one never leaves the directory without a binary), `NoDowngrade` (for dist-tag installs, published versions never go backwards; a concrete `install(version:)` is a legitimate downgrade and is not modelled), `LiveDownloadsIntact`, `StaleTempsSwept` (whoever holds the lock sees no temp files except its own, so disk use stays bounded after crashes).

**One reachable state is worth knowing.** Every upgrade briefly has `VERSION` naming v2 while the binary is still v1, in the window between writing the metadata and the rename. That window is held under the lock and is not the interesting part. `reach_mismatch_crash` and `reach_mismatch_fail` show something stronger: the shipped design can leave that mismatch behind with no install running. `lastHolderExit` records how the last lock holder left, which rules out the transient window. In one trace the process is killed after `Record` (`Verify → Record → Crash`). In the other the rename itself fails. `#publish`'s comment names both causes. The leftover state is harmless only because `installed?` re-hashes the binary instead of trusting `VERSION`. `Metadata.read` has no other caller. Anything that starts reporting "the installed version" from `VERSION`, or drops the re-hash, reintroduces the inconsistency.

## `ControlProtocol.tla`: outbound control requests

Models the outbound half of the control protocol in `lib/claude_agent_sdk/query.rb`: `send_control_request` / `await_control_response`, the read loop's `handle_control_response`, and the EOF broadcast in `read_messages`' `ensure`. There are two senders. One is a fiber of the reactor that owns the `Query`, the reactor its read loop runs on (`Async::Condition`, which checks the result slot and parks with no suspension point between them). The other is any caller that is not on the owning reactor: a FiberBoundary worker thread, a plain thread, or a fiber on another thread's reactor (`ThreadWaiter`, where the read loop can run between the check and the park). `send_control_request` picks the waiter by that ownership, not by whether the caller has an Async task. The CLI may answer each request or never answer, and it eventually exits. The model checks liveness under weak fairness. Control-request timeouts are left out on purpose, because the 1200 s deadline would make every liveness property hold trivially. What the model asks is whether a caller ever *needs* the timeout.

There are three properties. `EverySenderFinishes` says every control method returns or raises. `NoHalfExecutedRequest` says a method that fails locally never reached the CLI. `DeliveredMeansAnswered` says a response the read loop consumed is never replaced by the stream-end error; this holds because the broadcast uses `||=`. None of the variants below targets `DeliveredMeansAnswered`, but every config still checks it.

| Config | Switch | Result | The comment it checks |
|---|---|---|---|
| `good` | all `TRUE` | pass | |
| `bug_detect_after_write` | `DETECT_MODE_BEFORE_WRITE = FALSE` (the code before `420ee09`) | `NoHalfExecutedRequest` violated: the worker thread registers and writes the request, then `Async::Task.current` raises, and its `ensure` evicts the waiter. The CLI has the request, and its answer will be dropped by the `key?` guard | `send_control_request`: "Detecting after the write left a half-executed request (written to the CLI, then RuntimeError; the eventual response dropped by the key? guard)" |
| `bug_nonatomic` | `ATOMIC_REGISTRATION = FALSE` | `EverySenderFinishes` violated: a sender passed the stream-error check, EOF snapshotted the pending map before it registered, and it waits forever | `send_control_request`: "Register atomically with the terminal-state check so EOF cannot strand a sender that missed the final broadcast" |
| `bug_nocheck` | `CHECK_SLOT_FIRST = FALSE` | `EverySenderFinishes` violated: the fiber's write suspended after delivery, and the broadcast signal fired before it waited, so the signal was lost | `await_control_response`: "a signal arriving before the sender reaches wait would otherwise be dropped" |
| `bug_edge_thread` | `LEVEL_TRIGGERED = FALSE` | `EverySenderFinishes` violated: the sender off the owning reactor checked the slot, the signal fired before it parked, and the signal was lost. A fiber on another thread's reactor was in exactly this position while the waiter was picked by "has an Async task" | `ThreadWaiter`: "closing the check-then-wait gap that an edge-triggered Condition would lose across threads" |

## Next: `RunLifecycle.tla` (not written yet)

`Query::RunLifecycle` (`lib/claude_agent_sdk/query/run_lifecycle.rb`) decides when `query()` may close stdin: at the CLI's `idle` after a result, at a ceiling between turns, or at the first result with no tracked task in flight. Its fixes so far were all orderings between fibers — ending a run before stopping the ceiling sleeper, re-arming while a control request is in flight, the task ledger — and none of them is model-checked. The decision now sits in one Ruby file behind five events and one wait, so one model can cover it. Until it exists there is no model and no exhaustive check of the interleavings. What runs is RSpec: the lifecycle's table (`spec/unit/query/run_lifecycle_spec.rb`), and through a real `Query`, the end-before-clear ordering on the real scheduler (`spec/unit/query_end_run_order_spec.rb`, which CI also runs on the async 2.10 floor) and, in `spec/unit/query_run_end_spec.rb`, a hook parked under a passing ceiling, the mirror flush gated ahead of a result, and a close that begins while the read loop holds a result (from a reactor task and from another thread). Each covers only the interleavings its examples spell out.

What the model has to hold:

- **Per-run identity, not one `ended` flag.** A waiter keeps the run it started waiting on; a run that ended and was reopened still releases it. So: a sequence of runs, the current one, the set of ended ones, and the run each waiter captured.
- **Actions split at the handoffs.** Ending a run is three steps another fiber can run between: mark the run ended, signal its waiters, stop the sleeper. The input writer (`MessageWillWrite`) must be able to interleave with each. The other actions: a result, a session state, a main-thread turn, a task starting or settling, a control request starting or ending, the ceiling waking (armed, and its generation still current), stdin closing, empty input, the reader going away.
- **Switches**, one per rejected alternative: `END_BEFORE_CLEAR` (`FALSE`: the sleeper is stopped before the run is marked ended, and a message written in that gap joins the run that is about to end), `REARM_ON_CONTROL` (`FALSE`: a ceiling that passes under a control request ends the run), `TRACK_LEDGER` (`FALSE`: a result ends the run with a background agent still in flight).
- **Properties.** `NoCloseMidTurn`: stdin never closes during a turn or with a tracked task in flight, unless the reader is gone or the closing waiter's own run had ended. `MessageOwnsRun`: after a message is written, the current run is not ended until a later result, `idle` or the reader's exit — for single-message prompts; from a CLI that reports no state, a queued later message is a documented limitation, not a property. `EventuallyEnds`, under weak fairness and a ceiling above 0, given that timer-resetting work eventually stops (no endless `running` frames, tracked tasks or control requests after a result) and that an interval between turns eventually occurs.

## What the models assume and leave out

- File contents are abstracted to "the version they are the bytes of", so a checksum match is equality. Platform detection is not modelled.
- The models assume that POSIX `rename` is atomic and that the kernel releases a dead process's flock. `ReadersSeeVerifiedBinary` holds by construction given those assumptions.
- Durability is assumed, not modelled. `Crash` leaves the files as the completed steps left them, which is exact when a process dies. Across a power loss it rests on the installer's `fsync`s — the downloaded bytes before `Rename`, the `VERSION` bytes before `Record`'s rename, and (best-effort) the directory after `Rename` — and on `fsync(2)` reaching stable storage: a surviving name then holds a complete file, and a rename that had not reached the disk is undone, which is `Crash` at an earlier step on a filesystem that commits directory operations in order.
- Not modelled: `install`'s read-only shortcut. When the lock file cannot be opened (`EACCES`, `EROFS`, `EPERM`) and the request is a concrete version that is already installed and re-hashes to its recorded checksum, `install` returns the binary without the lock. That path takes no lock and writes nothing, so it is one more lock-free reader, which `ReadersSeeVerifiedBinary` already covers; no modelled ordering and no `run.sh` expectation changes.
- Not modelled: control-request timeouts (see above); the inbound half (`handle_control_request`, the #119 process-exit path, cancellation during a response write, which the transport answers by poisoning itself so no partial frame is ever followed by another); `Metadata.write`'s own temp file; `TranscriptMirrorBatcher`.
- **The Ruby is not verified.** A model can drift from the code it describes. When you change one of the orderings the tables cite, update the model and `run.sh`'s expectations in the same change. Each counterexample trace can also be turned into an RSpec regression by stubbing `CLIInstaller::Http` / `Release` / `Metadata`, or with a scripted transport for `Query`, so that the step TLC found is exercised against the real code.
